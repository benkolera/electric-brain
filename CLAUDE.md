# CLAUDE.md — Electric Brain

Project-specific guidance for Claude Code sessions on this repo.
General Phoenix 1.8 conventions live in `AGENTS.md` (read that too).

## North star

Read the README first. The product is organised around **balance
across life areas**, not throughput, and the Sunday planning ritual
is the use case to optimise for. When a change has tradeoffs, weight
toward the weekly-planning flow and the long-running streak / balance
view over one-off micro-features.

## Always keep these in sync with code changes

Treat these as part of the change, not follow-up work:

1. **`README.md`** — if you add, remove, or meaningfully change a
   user-visible feature (a category-level thing in the "What it does"
   list), update the README in the same commit. If you change the
   resource graph (new Ash domain, new cross-domain reference),
   update the Mermaid architecture diagram.
2. **Tests** — every change to an Ash resource, action, policy, or
   live view event should land with a matching test edit. The test
   suite is the only check that the planner / habits / time blocks
   stay correct as we iterate. Don't ship a schema change with no
   test movement; either update an existing test or add one.
3. **Ash snapshots** — `mix ash.codegen --name <descriptive>` after
   any resource/attribute/action edit. Never hand-edit migration
   files except for one-shot data moves (see "Migrations" below).

If you're unsure whether something needs README or test movement,
err on the side of yes.

## Conventions

- **Ash, not raw Ecto.** Resources, actions, policies. Use
  `Ash.Query`, `Ash.get!`, `Ash.read!`, `Ash.create!` etc. Don't
  reach into `Repo.*` unless you're inside a Release task.
- **Migrations**: `mix ash.codegen --name <name>` for schema
  changes. Write manual Ecto migrations only for one-shot data
  moves (the time-blocks split is the precedent — see
  `priv/repo/migrations/20260520102400_migrate_fixed_habits_…`).
  Manual migrations don't get a snapshot update.
- **Auth**: prod uses the Auth0 `oauth2` strategy on
  `Electricbrain.Accounts.User`. The `password` strategy is gated
  by `Mix.env() in [:dev, :test]` so dev can use the form auth and
  prod is Auth0-only. Don't reintroduce the password strategy in
  prod paths.
- **Per-entry duration override**: `Planner.Entry.duration_minutes`
  is the override; `(entry.duration_minutes || schedulable.duration_minutes
  || default)` is the canonical fallback chain. Reading the
  schedulable's `duration_minutes` directly is a bug — fixed-schedule
  time blocks set the override per-entry from the availability
  window, with the time block itself having `nil` duration_minutes.
  This bit us multiple times; the helper to use is
  `entry_duration_minutes/1` in `planner_live/index.ex`.
- **Schedulable polymorphism**: an `Entry` references exactly one
  of `todo_id`, `habit_id`, `time_block_id` (DB check constraint
  enforces it). Code that resolves "the thing being scheduled"
  needs to handle all three — the pattern is
  `entry.todo || entry.habit || entry.time_block`. Greppable
  helpers: `entry_schedulable/1`, `entry_title/1`,
  `entry_color_id/2`.
- **Time blocks ≠ habits**: time blocks (Sleep, Work) live in
  `Electricbrain.TimeBlocks`, not `Habits`. Habit-only features
  (identity, streak heatmap, neglect score) MUST NOT be applied to
  time blocks. The fixed_schedule boolean is gone; if you find
  yourself wanting it, the answer is "this should be a TimeBlock".
- **Categories form a strict tree** (no tags). Each has at most one
  `parent_id`. Code walking the tree must use `categories_by_id`
  (a flat map) and the `parent_id` field; never assume preloaded
  `parent` relationships. `Electricbrain.Categories.Colors.resolve_id/2`
  is the canonical parent-chain walk.
- **Calendar sync** (`Electricbrain.GoogleCalendar`) is idempotent
  via `entry.google_event_id`. The corollary: any handler that
  destroys or unschedules an entry MUST delete the Google event
  first (the `delete_from_google_if_synced/2` helper in
  `planner_live/index.ex`). Forgetting this leaks orphan Google
  events that duplicate on the next sync.
- **Timezones**: completions are stored UTC, bucketed by user
  local-day for display. Helpers in `Electricbrain.Timezones`.
  `period_start/3` only accepts `:day | :week | :month` — period
  is nil for time-block habits, so guard before calling it (the
  `Neglect.habit_score(%{period: nil}, …)` short-circuit clause is
  the pattern).
- **`mix precommit`** — always run before declaring a change done.
  Runs `compile --warnings-as-errors`, `deps.unlock --unused`,
  `format`, `test`.

## When in doubt

- Check `AGENTS.md` for Phoenix v1.8 + LiveView 1.1 + Tailwind v4
  conventions (autogenerated by `phx.new`, broadly correct).
- Check the README's architecture diagram for which domain a piece
  of behaviour belongs in.
- Prefer adding behaviour to an existing Ash resource over creating
  a new one; new domains are a real commitment.
- Don't add daisyUI components — the design language is hand-rolled
  Tailwind.
